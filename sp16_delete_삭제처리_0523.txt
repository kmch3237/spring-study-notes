====================================================================
  sp16_board — 게시물 삭제(delete) 흐름 완전 정리 (2026-05-23)
  목표: 게시판 CRUD 중 D(Delete) 부분을 혼자 쓸 수 있게!
====================================================================

■ 왜 따로 정리하나?
  - list / write 정리는 했는데 delete 부분이 빠져 있어서 보완.
  - 게시물 삭제는 "CRUD 4형제" 중 가장 단순한 편이지만,
    Controller → Service → Mapper → XML 의 4단계 흐름을
    가장 깔끔하게 보여주는 좋은 예시!

■ 비유로 이해하기
  ┌───────────────────────────────────────────────────────────┐
  │  게시판 삭제 = 도서관에서 책을 폐기하는 과정                │
  │                                                           │
  │  1) 사용자(독자)    : "이 책 폐기해 주세요!" (요청)        │
  │  2) Controller(접수): 요청 받아서 폐기 담당에게 전달        │
  │  3) Service(폐기팀) : 폐기 절차 진행 (예외 처리 포함)       │
  │  4) Mapper(서기)    : "○○책 폐기" 라고 장부에 기록         │
  │  5) XML(폐기서류)   : DELETE SQL 실행 → DB에서 사라짐       │
  └───────────────────────────────────────────────────────────┘

 [1] 전체 흐름 한눈에 보기
====================================================================

┌─────────────────────────────────────────────────────────────────┐
│                       글 삭제 전체 흐름                          │
│                                                                 │
│  사용자가 "삭제" 버튼 클릭                                       │
│       ↓                                                         │
│  GET /bbs/delete?num=10                                         │
│       ↓                                                         │
│  BoardController.delete(num)            ← (아직 미구현)         │
│       ↓                                                         │
│  boardService.deleteBoard(num)                                  │
│       ↓                                                         │
│  mapper.deleteBoard(num)                                        │
│       ↓                                                         │
│  bbsMapper.xml  <delete id="deleteBoard">                       │
│       ↓                                                         │
│  DELETE FROM BBS WHERE NUM = #{num}    ← Oracle 실행            │
│       ↓                                                         │
│  return "redirect:/bbs/list"  → 목록으로 돌아감                 │
└─────────────────────────────────────────────────────────────────┘

  ★ 핵심: insert/update/delete 는 끝나면 반드시 list로 redirect!
     → forward가 아니라 redirect 인 이유는 새로고침(F5) 했을 때
       삭제 요청이 또 날아가는 사고를 막기 위함이다.
       (= PRG 패턴: Post-Redirect-Get)

 [2] Service 인터페이스 — BoardService.java
====================================================================

  // 게시물 삭제
  public void deleteBoard(long num) throws Exception;

  ─────────────────────────────────────────────────────────────
   왜 long 타입인가?
  ─────────────────────────────────────────────────────────────
  - BBS 테이블의 NUM은 보통 시퀀스로 생성 → 점점 커진다.
  - int (약 21억) 까지는 충분하지만, 실무에서는 long 으로 잡는 게 안전.
  - Oracle 의 NUMBER 타입과도 잘 맞는다.

  ─────────────────────────────────────────────────────────────
   왜 throws Exception 인가?
  ─────────────────────────────────────────────────────────────
  - DB 작업은 언제든 예외가 터질 수 있다 (커넥션 끊김, 락 등)
  - 호출한 쪽(Controller)에서 try-catch 로 잡아서 로그 남기게 함.


====================================================================
 [3] Service 구현 — BoardServiceImpl.java
====================================================================

  // 게시물 삭제
  @Override
  public void deleteBoard(long num) throws Exception {
      try {
          mapper.deleteBoard(num);
      } catch (Exception e) {
          log.info("deleteBoard : ", e);
          throw e;
      }
  }

  ─────────────────────────────────────────────────────────────
   여기서 진짜 중요한 패턴 3가지
  ─────────────────────────────────────────────────────────────

  ① try-catch 로 감싸기
     → 어떤 메소드에서 예외가 났는지 로그로 추적하기 위함.

  ② log.info("deleteBoard : ", e);
     → 메소드명을 로그에 직접 박아둠.
       (스택트레이스만 봐선 어느 메소드인지 빨리 안 보임)

  ③ throw e;  ★★★ 가장 중요!
     → 잡았으면 다시 던져야 한다.
     → 이유: Controller 가 "삭제가 성공/실패 했는지" 알아야
       사용자에게 메시지를 보내거나 분기 처리할 수 있기 때문.
     → throw e 가 없으면 Controller 입장에서는
       "성공한 줄 알고" 그대로 list 로 redirect 해버린다.

 [4] Mapper 인터페이스 — BoardMapper.java
====================================================================

  @Mapper
  public interface BoardMapper {
      ...
      public void deleteBoard(long num) throws Exception;
      ...
  }

  ─────────────────────────────────────────────────────────────
   핵심 규칙
  ─────────────────────────────────────────────────────────────
  - 메소드명(deleteBoard) = XML의 id(deleteBoard) 와 반드시 일치!
  - 인터페이스만 만들고, 구현체는 만들지 않는다.
    → MyBatis가 자동으로 구현체를 만들어준다. (Proxy)
  - @Mapper 어노테이션은 생략 가능 (mybatis-spring:scan 설정 시)

 [5] bbsMapper.xml — 실제 SQL
====================================================================

  <!-- 삭제 -->
  <delete id="deleteBoard" parameterType="long">
      DELETE FROM BBS WHERE NUM = #{num}
  </delete>

  ─────────────────────────────────────────────────────────────
   요소별 의미
  ─────────────────────────────────────────────────────────────

  ┌─────────────────────┬─────────────────────────────────────┐
  │ 요소                │ 의미                                │
  ├─────────────────────┼─────────────────────────────────────┤
  │ <delete>            │ SQL이 DELETE 문이라는 선언          │
  │ id="deleteBoard"    │ 인터페이스 메소드명과 동일해야 함   │
  │ parameterType="long"│ 받는 파라미터 타입 (num)            │
  │ #{num}              │ ? 자리 (PreparedStatement, 안전!)   │
  └─────────────────────┴─────────────────────────────────────┘

  ★ #{} 와 ${} 차이 (자주 헷갈림!)
     #{num}  → ? 로 치환 → 값에 사용 (SQL Injection 방어)
     ${num}  → 그대로 치환 → 테이블명/컬럼명 등 동적 식별자에만!

  ※ delete 에서 ${} 쓰면 절대 안 됨!
    예: WHERE NUM = ${num}  로 하면
    사용자가 "1 OR 1=1" 같은 값을 넣어버리면 전체 글이 삭제됨.

 [6] Controller — 아직 미구현! (예측 코드)
====================================================================

  ※ 5/22 기준 BoardController.java 에는 delete 메소드가 없음.
    Service/Mapper/XML 까지는 모두 준비 완료.
    아래는 흐름상 곧 추가될 것으로 예상되는 코드.

  ─────────────────────────────────────────────────────────────
   가장 단순한 버전 (인증 없이 바로 삭제)
  ─────────────────────────────────────────────────────────────

  @GetMapping("delete")
  public String delete(@RequestParam("num") long num) {

      try {
          boardService.deleteBoard(num);
      } catch (Exception e) {
          log.info("delete : ", e);
      }

      return "redirect:/bbs/list";
  }

  ─────────────────────────────────────────────────────────────
   실무용: 비밀번호 확인 후 삭제 (예상 버전)
  ─────────────────────────────────────────────────────────────

  @PostMapping("delete")
  public String deleteSubmit(@RequestParam("num") long num,
                             @RequestParam("pwd") String pwd) throws Exception {

      // 1. 글 정보 조회
      Board dto = boardService.findById(num);

      // 2. 비밀번호 일치 확인
      if (dto == null || !dto.getPwd().equals(pwd)) {
          // 일치 안 하면 다시 폼으로
          return "redirect:/bbs/article?num=" + num;
      }

      // 3. 일치하면 삭제
      boardService.deleteBoard(num);

      return "redirect:/bbs/list";
  }

 [7] CRUD 4형제 한눈에 비교
====================================================================

  ┌──────────┬─────────────┬────────────────┬─────────────────────┐
  │ 동작     │ SQL         │ XML 태그       │ Mapper 메소드       │
  ├──────────┼─────────────┼────────────────┼─────────────────────┤
  │ 등록(C)  │ INSERT      │ <insert>       │ insertBoard(dto)    │
  │ 조회(R)  │ SELECT      │ <select>       │ findById(num) 등    │
  │ 수정(U)  │ UPDATE      │ <update>       │ updateBoard(dto)    │
  │ 삭제(D)  │ DELETE      │ <delete>       │ deleteBoard(num)    │
  └──────────┴─────────────┴────────────────┴─────────────────────┘

  ★ 공통점
    - C/U/D 는 끝나면 list 로 redirect
    - R(조회) 는 forward (그 화면을 보여줘야 하니까)

  ★ 차이점
    - C(insert)/U(update) → DTO 통째로 받음 (parameterType=Board)
    - D(delete)         → num 하나만 받음   (parameterType=long)
    - R(select)         → 결과를 받아옴     (resultType 필수)

 [8] sp14 (XML 기반) vs sp16 (Annotation+MyBatis) 비교
====================================================================

  ┌──────────────────┬────────────────────┬─────────────────────────┐
  │ 항목             │ sp14 (XML 방식)    │ sp16 (Annotation 방식)  │
  ├──────────────────┼────────────────────┼─────────────────────────┤
  │ DB 접근          │ DAO + JdbcTemplate │ Mapper 인터페이스       │
  │ SQL 위치         │ DAO 자바 코드 안   │ bbsMapper.xml 별도 파일 │
  │ 삭제 메소드      │ dao.deleteBoard()  │ mapper.deleteBoard()    │
  │ 구현체 작성      │ 직접 작성          │ MyBatis가 자동 생성     │
  │ 파라미터 바인딩  │ ?, setLong()       │ #{num} (자동 바인딩)    │
  └──────────────────┴────────────────────┴─────────────────────────┘

  ★ 결론
    sp16 으로 오면서 "SQL과 자바 코드가 분리" 되어
    SQL 수정 시 자바 재컴파일이 필요 없어졌다.
    그리고 구현체를 작성 안 해도 되니까 코드량이 확 줄어든다.

 [9] 주의사항 정리
====================================================================

  ① delete 후에는 반드시 redirect!
     → forward 하면 새로고침 시 또 삭제 시도 (이미 없는 글이라 에러)

  ② #{} 만 쓸 것. ${} 절대 금지
     → SQL Injection 으로 전체 글이 날아갈 수 있음

  ③ throw e 빼먹지 말 것
     → Service 에서 잡고 다시 던져야 Controller 가 알 수 있음

  ④ 실무에서는 "실제 삭제" 보다 "삭제 플래그(soft delete)" 가 일반적
     → 예: DELETE 대신 UPDATE BBS SET DEL_YN='Y' WHERE NUM=#{num}
     → 데이터 복구/감사 추적이 가능하기 때문

  ⑤ 비밀번호 확인은 Controller 가 아니라 Service 에서 하는 게 더 좋음
     → 책임 분리 (SRP 원칙)
